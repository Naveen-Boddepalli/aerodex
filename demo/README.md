# demo/ — synthetic dataset for demos and screenshots

> **None of this is a measurement.** Every fare here comes from the fixture
> adapter (`source='fixture'`), which makes no network calls and prices nothing
> real. The publisher refuses this data unless `allow_synthetic=True` is passed
> explicitly. Do not put a number from this folder in a slide that claims to
> show Indian airfares.

It exists because a demo needs more than `tests/golden/panel.csv` offers. The
golden panel is 4 periods and 3 routes — correctly so, because it is a
regression fixture that a human has to be able to read. That shape gives a
dashboard almost nothing to draw and leaves the coverage machinery with nothing
to act on. This folder is 30 periods across the full 60-route panel, so the
charts have a series and the M5 path has a hole to handle.

Everything here is regenerated by one command, with no Docker, no database and
no network:

```bash
uv run python scripts/make_demo_data.py
```

That run is deterministic — fixed dates, a hash-seeded adapter, no clock reads,
and gzip written with `mtime=0`. Regenerating reproduces all 11 files
byte-for-byte, so a changed `sha256` in `MANIFEST.json` means an input actually
moved.

## What is in here

| File | What it is |
| --- | --- |
| `panel.csv.gz` | The main panel — 75,552 rows, 30 daily periods, 60 routes × 7 horizons |
| `index.csv` / `index.json` | The index computed from it, DGCA-weighted |
| `expected_hashes.json` | Frozen M6 hashes for `aerodex verify` |
| `artifacts/` | What the publisher emits: `index_latest.json`, `index_full.csv`, `methodology.json`, `release-2026-09-30.json` |
| `breach/panel.csv.gz` | The same collection with a large coverage hole — breaches M5 |
| `breach/index.csv` | Its index, carrying `imputation_ceiling_breached` |
| `MANIFEST.json` | Provenance, shape, hashes, and the festival calendar behind the shape |

## Using it

Compute the index from the panel — no database needed:

```bash
uv run python -m aerodex.cli index --panel-csv demo/panel.csv.gz
```

Run the M6 reproducibility check over 30 periods instead of the golden four:

```bash
uv run python -m aerodex.cli verify --panel-csv demo/panel.csv.gz --hashes demo/expected_hashes.json
```

Show the publisher refusing a run whose imputed weight breached the ceiling:

```bash
uv run python -m aerodex.cli index --panel-csv demo/breach/panel.csv.gz
```

## The shape, and why it moves

The panel runs `2026-09-01` → `2026-09-30`, which is the base period declared
in `config/methodology.yaml` (`base.period: "2026-09"`). Starting anywhere else
would put the index's own base month outside the data.

The index opens at 100.00 and closes at **107.44**, dipping to 97.44 and
peaking at 109.78. It moves for three disclosed reasons, applied on top of the
adapter's own fare noise — the raw fixture fare is a hash and produces a flat
line that demonstrates nothing:

- **Festivals.** Departures inside a window from `config/calendar.yaml` carry a
  1.35× surge, ramped in across that festival's own `lead_days`. Because the
  panel is constant-horizon, one festival reaches the 1-day and 60-day strata
  on *different* collection dates — the 60-day horizon books Diwali in late
  September while the 1-day horizon has not seen it yet. That staggering is the
  single most useful thing in this dataset to point at. Five festivals fall in
  range: Ganesh Chaturthi, Durga Puja, Dussehra, Diwali, and the Christmas/New
  Year run-up.
- **Weekends.** Friday and Sunday departures 1.08×, Saturday 1.04×.
- **Trend.** A mild 1.0002× per day of departure date.

This is the same convention `scripts/make_golden_panel.py` already uses when it
builds in a "deliberate upward trend", and it is disclosed in
`MANIFEST.json → demand_shaping`. It is the only reason a number here moves in
a way a fixture fare would not.

## The two coverage holes

Both are cut on `(route, horizon, period)` rather than by dropping whole
routes. That distinction matters: a route that vanishes entirely leaves its
horizon group with no sibling to impute from, so the strata are dropped and
renormalised away — coverage falls but the *imputed share stays zero*, which
demonstrates nothing about M5. Cutting only some of a route's horizons leaves
siblings reporting, so the gap is genuinely imputed and the published share
moves.

**`panel.csv.gz`** — BLR–CCU loses its 1-day and 3-day horizons for four days
(`2026-09-12` … `09-15`). Coverage drops to 0.99524, imputed weight share rises
to 0.00579 — real, visible, and under the 0.05 ceiling, so the run publishes
and `artifacts/` exists.

**`breach/panel.csv.gz`** — five horizons across the three heaviest routes
(DEL–BOM, BOM–DEL, DEL–BLR) drop for three days. Imputed weight share reaches
**0.11928**, well past the ceiling, and four periods are flagged
(`2026-09-21` … `09-24`; the hole spans three collection dates but the index
compares periods pairwise, so the day after the hole is affected too). The
publisher refuses the whole run:

> imputed weight share exceeded 5% (M5) for period(s): … Publish the coverage
> failure, not a prettier number.

There is deliberately no `breach/artifacts/`. That absence is the point.

## Regenerating with a different shape

```bash
uv run python scripts/make_demo_data.py --start 2026-10-01 --days 60 --out demo
```

`--start`, `--days` and `--out` are the only knobs. Changing the start date
moves which festivals land in range, and the hole offsets move with it. If you
change `--days` below about 23 the breach window falls outside the series and
the script exits with `FATAL: the breach panel did not breach` — retune
`BREACH_HOLE` in the script rather than removing the assertion, since that
assertion is what stops a demo from silently shipping a panel that no longer
demonstrates the refusal.
